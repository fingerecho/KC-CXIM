克铖 《铖信即时通讯》
一个完整的即时通讯软件通常由客户端、服务端、管理后台三大主体构成，底层依赖网络接入与存储等基础设施来支撑消息的实时收发与数据持久化。

客户端
这是用户直接交互的部分，通常以 App、Web 或桌面应用形式存在，核心职责是连接与展示。
多端覆盖与 SDK：提供 Android、iOS、Web、小程序及 PC 端 SDK，封装通信协议，方便业务方快速集成。
核心功能模块：包含注册登录、单聊/群聊界面、联系人（好友）管理、会话列表、消息输入与展示（支持文本、表情、图片、语音、文件等）、个人中心及设置等。
本地存储与同步：在无网或弱网时缓存消息，并在网络恢复后与服务器同步，保证多端消息一致。

服务端
这是系统的核心大脑，负责处理所有业务逻辑、连接管理与消息路由。
接入层：维持海量用户的长连接（通常基于 TCP 或 WebSocket），负责协议解析、心跳保活及初步的安全防护。
逻辑层：处理登录鉴权、单聊消息转发、群聊扩散、离线消息存储、消息撤回、敏感词过滤等核心业务逻辑。
路由与状态管理：通过缓存（如 Redis）记录用户在线状态及所在的网关地址，确保消息能精准投递到目标用户当前在线的设备上。
第三方推送对接：当用户离线时，服务端需对接 APNs（iOS）、FCM 或厂商推送通道（安卓），将新消息提醒送达用户。

管理后台（Web 控制台）
这是供运营和管理员使用的 B/S 架构平台，用于维护系统秩序。
用户与权限管理：支持用户资料的增删改查、封禁/解禁用户、角色权限配置。
应用配置与监控：管理 App 的基本配置、查看服务运行状态、统计数据及系统日志。
内容审核：管理敏感词库、处理违规内容举报等。

基础支撑与存储
这部分是隐藏在后端的基石，决定了系统的扩展性与可靠性。
存储层：使用关系型数据库（如 MySQL）存储用户资料与关系链；使用 NoSQL（如 HBase、MongoDB）或对象存储来海量存储消息历史与文件（图片、语音）。
消息队列：在高并发场景下，利用 Kafka 或 RocketMQ 进行削峰填谷，解耦消息的接收与投递过程。
音视频服务：若包含实时音视频通话或会议功能，通常需要独立的流媒体服务器或集成第三方 RTC 服务。

特别说明：在实际工程中，现代 IM 系统往往强调业务与通讯分离。核心通讯组件只负责“管道”功能（即把数据无差错地送达），而具体的业务逻辑（如红包、订单通知、动态发布）则由外部业务系统通过 API 或自定义消息类型来调用通讯组件实现。

后端介绍

IM 后端需要分层组合：对外入口用 API 网关，内部同步调用用 RPC，消息流转用消息队列，服务地址管理用注册中心。这几个组件各司其职，共同把拆散的服务组织成一个可运行的系统。

API 网关
它是客户端访问后端的唯一入口，负责鉴权、路由、限流，把外部请求转发到内部服务。IM 项目中通常同时存在 HTTP API 网关（处理用户、好友、群组等 REST 请求）和 WebSocket 长连接网关（处理消息收发与推送）。

服务注册与发现中心
服务实例的地址会因扩缩容而变动，注册中心让服务能互相“找到”对方。常用选型如 Consul、Nacos 等。IM 项目中有使用 Consul 配合 gRPC 做服务发现的实践。

RPC 框架
用于内部服务之间的同步高频调用，比如消息服务调用用户服务校验关系、群组服务调用关系服务拉取成员列表。IM 场景对延迟敏感，gRPC 基于 HTTP/2 和 Protobuf，性能优于 REST，是常见选择。

消息队列
用于异步解耦和削峰。IM 的典型场景是：消息写入后，通过 MQ 异步触发持久化、推送、离线通知等下游动作，避免主链路被拖慢。参考架构中，msg.rpc 生产消息到 Kafka，再由独立的消费者服务完成持久化和推送分发。常用选型包括 Kafka、RocketMQ。

客户端
  │
  ├── HTTP ──▶ KC-CXIM-Gateway (API 网关) ──gRPC──▶ 用户/好友/群组等 RPC 服务
  │
  └── WebSocket ──▶ KC-CXIM-MsgGateway (长连接网关)
                          │
                          ├──gRPC──▶ 消息 RPC 服务（消息发送/撤回/已读）
                          │
                          └──▶ 消息队列 (Kafka/RocketMQ)
                                    │
                                    ├──▶ 持久化消费者服务
                                    └──▶ 推送消费者服务

所有 RPC 服务启动时向注册中心注册，网关和调用方从注册中心获取可用实例地址。配置管理可以额外引入配置中心（如 Nacos Config），但这属于辅助设施，不是组织服务通信的核心。
