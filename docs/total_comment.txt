MariaDB选用连接池还是单连接？
应该用连接池，不建议长期用单连接。 但有一个更重要的前提要先说清楚：你的服务目前是单线程 io_context + 阻塞式 MariaDB C++ 驱动，所以"连接池"能不能发挥价值，取决于你是否把 DB 操作放到独立的工作线程里。
1. 为什么不该用"单连接"
单连接意味着所有 SQL 串行执行，并且有几个硬伤：
- 事务会互相污染：如果多个调用方共用同一条连接，A 的 BEGIN 还没 COMMIT，B 的 SQL 就跑进了 A 的事务里，数据会错乱。事务必须"一条连接一次独占"。
- 单点故障：这条连接断了，整个服务的 DB 能力瞬间归零。
- 无法并发：发消息要依次做「分配 seq → 插消息 → 写离线队列 → 更新回执」，单连接会把所有用户的这些步骤排成一队。
- 重连成本：每次断线都要重新 TCP + 认证。
对 IM 这种"每条消息多次写库 + 高并发"的场景，单连接在用户量稍大时一定是瓶颈。
2. 关键前提：别在 io_context 线程里做阻塞查询
MariaDB Connector/C++ 是同步阻塞 API。如果你直接在 session 的异步回调里执行 executeQuery()：
- 一次慢查询会卡住整个 io_context，所有连接收发全部停摆；
- 这时哪怕你有 8 条连接池，也用不上——因为只有一个线程在跑。
所以推荐架构是：
网络线程(io_context)  --投递任务-->  DB 工作线程池(2~4 线程)  --借用-->  连接池(4~8 条)
        ^                                                              |
        +------------------ post 回结果（写回 socket）-----------------+
- 网络层继续用 Asio 异步；
- DB 操作丢给工作线程池执行；
- 结果通过 boost::asio::post 回到 io_context 再写回客户端；
- 每个工作线程从池里 checkout 一条连接，用完 return。
3. 池开多大
- 2 核 2G、max_connections=100：4~8 条足够，最多 8~16。
- 经验公式：池大小 ≈ DB 工作线程数 + 少量余量。线程只有 4 个，池开到 50 没意义，只会白占内存。
- 给 root、备份、运维留余量，应用侧总连接数别逼近 100。
- 每条连接保持 connect timeout、会话状态重置（USE/事务/临时表不要残留）。
4. 你现在的阶段怎么选
阶段	建议
刚接入、联调、低流量 MVP	1 个 DB 工作线程 + 1~2 条连接最简单，先把链路跑通；但别在 io 线程里直接查库
正常上线/多用户	线程池 24 + 连接池 48
用户量上来	再按压测调大，同时考虑读写分离/分库
也就是说：单连接只适合"最初的联调阶段"，不作为目标架构。你现在问"池还是单连接"，答案是以连接池为目标设计，起步可以用小池（2 条），而不是一条全局连接。
5. 连接池的注意点
- 一个事务固定占用一条连接，绝不能跨线程共享同一条连接同时用。
- 借出/归还用 RAII（析构自动归还），异常也要归还。
- 断线重连 + 健康检查（如空闲 ping / 取用时校验），避免拿到死连接。
- MariaDB Connector/C++ 自带 MariaDbDataSource 的 pooled connection 机制（头文件里有 getPooledConnection() 及 "closes corresponding connections pool" 说明），也可以自己用 std::mutex + std::queue<unique_ptr<sql::Connection>> 实现一个简单池；自实现更可控，内置的更省事。
- 驱动 sql::mariadb::get_driver_instance() 是单例，可共享；连接对象不可共享。
如果你后面要我落地，我建议的实施顺序是：先做"DB 工作线程 + 小连接池的封装类"，再把发消息事务（seq/消息/离线队列/回执）接进去，最后加断线重连和健康检查。
