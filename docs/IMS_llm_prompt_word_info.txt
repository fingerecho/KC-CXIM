请问既然我的注册登录功能走HTTP短连接，那么我是不是应该单独再起一个进程处理这些短连接，Token能够跨进程共享吗？
答案：不应该再起一个进程处理。

server 旁边再挂一个 HTTP acceptor同一事件循环 或者 io.run() 起多线程，哪一种解决方案更好？为什么？
答案：io.run()单线程，即：server 旁边再挂一个 HTTP acceptor同一事件循环更好。原因是它恰好匹配现有的线程模型。

这样操作io.run()单线程，单线程io_context 会被注册请求卡死吗？为什么？
答案：不会因为"注册请求多"就卡死，但取决于 handler 里干了什么。异步本身不阻塞——accept/read/write 都是 async_*，回调只负责解析、入队、写回，很快返回；请求再多也只是排队。
真正会卡死单 io 线程的是在回调里做阻塞或长时间 CPU 操作：
1. 同步 DB 查询：会卡。但你现在的 Db 已经把 SQL 丢给 worker 线程（db.cpp:196-203，submit 只入队就返回），io 线程不碰 JDBC/MySQL，所以这块安全。
2. 密码哈希（bcrypt/argon2）：这是注册/登录最典型的坑。bcrypt cost=12 一次约 200–300ms 纯 CPU，如果在 HTTP handler 或 DB 层"io 侧"算，这 200ms 内所有连接的读写全部停摆。必须把哈希放进 worker job 里算。
3. RSA 签名、慢日志/同步文件 I/O、同步 DNS：同理，也都在 io 线程上会阻塞。HS256 签名很便宜，无所谓。
4. 注意 db.cpp:251 现在是明文比较，暂时不吃 CPU；一旦改成 bcrypt 校验，如果忘了挪到 worker，就会踩上面第 2 条。
另一个要注意的：submit 队列无界、不阻塞，io 线程不会被反压卡住；但 worker_count=2，如果哈希和 SQL 都塞进同一批 worker，慢哈希会造成队头阻塞，用户消息处理被拖慢。建议加密码/哈希时要么单独开一个 CPU 线程池，要么提高 worker 数并区分任务类型。
一句话：单线程 io_context 不会被异步注册请求"卡死"，只会在你把阻塞/重 CPU 活放在 io 线程上时卡死。把哈希和 SQL 都留在 worker，io 线程只做收包、JSON 解析、入队、回写即可。

1. 架构：同一进程、同一个单线程 io_context（io.run() 不增加线程）里，在现有 TCP acceptor 旁再挂一个 HTTP acceptor 处理注册/登录短连接，http服务使用Boost.Beast。
