请问既然我的注册登录功能走HTTP短连接，那么我是不是应该单独再起一个进程处理这些短连接，Token能够跨进程共享吗？
答案：不应该再起一个进程处理。

server 旁边再挂一个 HTTP acceptor同一事件循环 或者 io.run() 起多线程，哪一种解决方案更好？为什么？
答案：io.run()单线程，即：server 旁边再挂一个 HTTP acceptor同一事件循环更好。原因是它恰好匹配现有的线程模型。

这样操作io.run()单线程，单线程io_context 会被注册请求卡死吗？为什么？
答案：不会因为"注册请求多"就卡死，但取决于 handler 里干了什么。异步本身不阻塞——accept/read/write 都是 async_*，回调只负责解析、入队、写回，很快返回；请求再多也只是排队。
真正会卡死单 io 线程的是在回调里做阻塞或长时间 CPU 操作：
1. 同步 DB 查询：会卡。但你现在的 Db 已经把 SQL 丢给 worker 线程（db.cpp:196-203，submit 只入队就返回），io 线程不碰 JDBC/MySQL，所以这块安全。
2. 密码哈希（bcrypt/argon2）：这是注册/登录最典型的坑。bcrypt cost=12 一次约 200–300ms 纯 CPU，如果在 HTTP handler 或 DB 层"io 侧"算，这 200ms 内所有连接的读写全部停摆。必须把哈希放进 worker job 里算。
3. RSA 签名、慢日志/同步文件 I/O、同步 DNS：同理，也都在 io 线程上会阻塞。HS256 签名很便宜，无所谓。
4. 注意 db.cpp:251 现在是明文比较，暂时不吃 CPU；一旦改成 bcrypt 校验，如果忘了挪到 worker，就会踩上面第 2 条。
另一个要注意的：submit 队列无界、不阻塞，io 线程不会被反压卡住；但 worker_count=2，如果哈希和 SQL 都塞进同一批 worker，慢哈希会造成队头阻塞，用户消息处理被拖慢。建议加密码/哈希时要么单独开一个 CPU 线程池，要么提高 worker 数并区分任务类型。
一句话：单线程 io_context 不会被异步注册请求"卡死"，只会在你把阻塞/重 CPU 活放在 io 线程上时卡死。把哈希和 SQL 都留在 worker，io 线程只做收包、JSON 解析、入队、回写即可。

在本项目（Boost.Asio 单 io_context 的 IM 服务）中实现注册/登录功能，遵循以下约束：
1. 架构：同一进程、同一个单线程 io_context（io.run() 不增加线程）里，在现有 TCP acceptor 旁再挂一个 HTTP acceptor 处理注册/登录短连接，http服务使用Boost.Beast。

  改掉的真 bug：

  1. HTTP keep-alive 自己造 503 风暴（最严重）。inflightCount 原来在 http_session 构造/析构加减，但对象被 60s

     -1，加减天然成对），并在 close_socket() 里补上 idle_timer_.cancel()（TCP 侧 do_close()
     一直是这么做的，我之前漏了）。
  2. 关系缓存的 put-after-erase 竞态：worker X 缓存未命中读到 (1,1)，Y 在这期间提交"删除/拉黑"并
     erase（此时缓存里还没有那条 → 空操作），X 随后写回 → 一条已过期的"是好友"记录活满整个
     TTL。这正好命中项目自己定的红线"拉黑即时生效"。加了 relEpoch_ 版本号：任何 erase
     递增，读时记版本、写回时版本变了就放弃缓存。
  3. P1-2 的核心承诺没兑现：我把关系 SELECT 放在了 runTransactionWithRetry 之外，所以 TOCTOU
     只是变窄，而注释写的是"同一事务内、消除窗口"——注释比实现更乐观是最坏的一种错。已把 SELECT
     移到事务体内（缓存未命中路径），缓存命中路径的 TTL 窗口则如实写进注释与文档。
  4. 批量删好友漏推事件 + 计数撒谎：单条删除会向双方推 FriendListChanged，批量一条没推——被删的 20
     个人完全不知道列表变了。而 deleted=requested 是假的（DELETE 是双向两行，还包含单向拉黑行）。现在 DAO
     先读"哪些确实是我的好友"，回传真实 id 列表，HTTP 层逐个推双向事件，deleted 用真实人数。
  5. 批量建申请的附言 resize(255)：按字节切断中文 → MariaDB 严格模式报错 → 一条多行 INSERT 让整批 50

     桶是反滥用，必须宽于容量闸门，否则共享出口 IP 的真实用户和"一台机器发 100
     个用户注册+登录"的压测会在服务器空闲时被大面积 429。改成 30/s(burst 120)，并在 build.sh/readme
     写明为什么不能反过来配；同时给压测客户端加了按 Retry-After 的退避重试（http_call_once
     保持单次语义），否则"服务端正确地拒绝过载"会被记成"服务端出错"。
  7. 软/硬两级队列的洞：28 个走 submit() 的 DAO 不受 DB_QUEUE_LIMIT 约束却挤在同一条 sqlQueue_
     里，于是热路径会被它们的积压撞出 busy 拒绝，而新请求还在继续进——倒置的背压。现在 HTTP 准入同时看
     Db::sqlQueueDepth()，在往队列里塞任务之前就拒。
  8. 缓存淘汰里的潜在 UB：relLru_.erase(relLruIters_[key]) 用 operator[]，key 缺失时默认构造一个无效 list 迭代器再去
     erase。改成 find() + 守卫。
  9. 413 会吃掉自己的响应：请求体超限时还有未读字节，shutdown_both + close 让内核发 RST，刚写出去的 413
     可能被客户栈丢弃。改成只 shutdown_send。
